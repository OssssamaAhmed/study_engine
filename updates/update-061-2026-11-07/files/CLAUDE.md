# Study Engine — Architecture & Conventions

Local, single-user Laravel app for Spaced Interleaved Retrieval Practice, run as two independent tracks — AI Security Engineer and Laravel Web Development — switched from a dashboard toggle. Full requirements: `PROJECT_SPEC.md` (the source of truth for the original single-track build — read it before building anything; it predates the dual-track system, see "Dual study tracks" below).

## Status

All 6 original milestones complete, plus a later dual-track system (see "Dual study tracks" below). Pages: dashboard `/` (stats + Mission + the AI Security/Laravel Web track toggle), `/ingest`, `/chat` (tutor chat), `/exercise/{id}` (submit + evaluation; sticky "On this page" outline built client-side from mission h2/h3 — layout JS + `.toc-link` CSS, hooks: `#mission-toc` aside + `article.mission[data-outline]`), `/concepts` (`?filter=due|struggling`, retire toggle, struggle-note resolve, paginated 20/page), `/history` (paginated 20/page), `/settings` (provider display + resync roadmap + danger-zone reset, all per active track), `/side-quest` (targeted micro-drills; learner describes confusion → focused drill sequence; 0–20 drills, 0–10 boss fights, numeric), `/phases` (roadmap timeline — all phases, completion status, topic coverage per phase), `/phases/{n}` (single phase detail — Mega Portfolio Project generate/submit/evaluate; score ≥70 = passed; `PhaseService::generateMegaProject` / `evaluateMegaProject` / `markPhaseCompleted`), `/exam-prep` (exam prep engine — ingest study guide, choose method: active_recall/spaced_1357/test_maker/metacognitive, run session; `ExamPrepService`; `ExamPrepSession` model), `/exam-prep/session/{id}` (session detail + submit for evaluation), `/notifications` (exam alerts + system notifications; `NotificationService`), `/debug/topics`. `php artisan llm:test` smoke-tests the active provider. ## Key decisions

- **Embeddings**: JSON column on `chunks` + cosine similarity in PHP (not sqlite-vec — impractical to load on Windows PHP; hundreds of chunks makes PHP-side cosine fine).
- **Dual study tracks**: `App\Support\StudyMode` (`ai_security` | `laravel_web`) is the single source of truth for which track is active — session-based (dashboard toggle only, `POST /settings/mode`; never `.env`/CLI), with a flat-file fallback (`storage/app/private/active-mode.txt`) so terminal commands stay track-aware without a session. Unified schema, not duplicated tables: `App\Models\Concerns\ScopedToMode` (applied to `Topic`, `Transcript`, `Concept`, `Chunk`, `Exercise`, `PhaseProgress`, `Notification`, `ExamPrepSession`) registers a global Eloquent scope filtering every query to the active `mode` column and auto-stamps `mode` on create — every pre-existing call site across every service/controller needed zero changes. Bulk ops that bypass Eloquent (`syncTopics()`'s `DB::table('topics')->upsert()`, the raw deletes in `/settings/reset`) set `mode` explicitly since upsert/raw queries see neither model events nor global scopes. `topics.phase_number`/`phase_progress.phase_number` are unique on `(phase_number, mode)`, not alone — both tracks number their phases from 1. Laravel Web's curriculum is `storage/app/roadmap/Laravelstudy.json` (exact filename, targeted explicitly by `RoadmapService::load()`/`activeFilePath()`, never globbed like the AI file — the two coexist in the same folder). The 5 LLM prompts in `resources/prompts/` stay single-source, not forked: `{{TRACK_ROLE}}` / `{{TRACK_ROLE_WITH_ARTICLE}}` / `{{TRACK_ROADMAP_DESC}}` / `{{TRACK_QUALITY_DIMENSION}}` / `{{TRACK_FORESHADOW_EXAMPLES}}` / `{{TRACK_EVALUATOR_TITLE}}` / `{{TRACK_PROBLEM_LABEL}}` / `{{TRACK_PROBLEM_EXAMPLES}}` / `{{TRACK_PROBLEM_RATIONALE}}` / `{{TRACK_CONSIDERATIONS}}` / `{{TRACK_ARCHITECT_TITLE}}` / `{{TRACK_FLAW_LABEL}}` tokens are substituted per-track by `StudyMode::renderPrompt()` before every LLM call. Isolated per track: `ActivityLog` streaks (`activity-days-{mode}.txt`, two independent files), tutor chat (session key `chat_{mode}`, two independent conversations), all study data. Shared across both tracks by design (confirmed decision, not an oversight): Personal instructions and the learner's name — they describe the learner, not the track. `ChatController::learnerState()`'s struggle-note query uses `->whereHas('concept')` specifically so it never leaks the other track's notes into a tutor reply (`struggle_notes` has no `mode` column of its own — it scopes transitively through `concept_id`, same as `attempts` through `exercise_id`).
- **Curriculum truth**: the JSON in `storage/app/roadmap/` — `App\Services\RoadmapService::load()` globs `storage/app/roadmap/*.json` for AI Security (falling back to the first `*.json` at repo root if that dir is empty), and reads `storage/app/roadmap/Laravelstudy.json` explicitly for Laravel Web — no caching, re-read from disk every call. **Nothing in code copies the root JSON into `storage/app/roadmap/` for either track** — "Resync roadmap" (`POST /settings/resync`) just re-runs `syncTopics()` on whatever is already sitting in `storage/app/roadmap/` (upsert keyed on `(phase_number, mode)`, idempotent). Both tracks follow the same convention: the root-level JSON (`AI_Engineering_Roadmap_*.json`, `Laravelstudy.json`) is the master copy you hand-edit; to pick up edits, copy it into `storage/app/roadmap/` yourself, then resync. **The root `Laravelstudy.json` uses a different, simpler JSON shape than what `RoadmapService` parses** (a bare array of `{phase_number, title, description, week_start, week_end, topics:[{name,description}]}`, no `meta`/`phases` wrapper) — it's the source content, not something you can just drop into `storage/` verbatim; reshape it into `{meta, phases:[{phase,title,weeks,notes}], checkpoints:[], certifications:[]}` first (`notes` is what `PhaseService::generateMegaProject()` actually reads; the original `topics` array is worth preserving alongside `notes` for reference even though nothing parses it today). GOTCHA: as of this writing the AI pair is out of sync too — root is `AI_Engineering_Roadmap_v3.2_Karpathy_Updated.json`, `storage/app/roadmap/` still has the older `AI_Engineering_Roadmap_v3_1.json`.
- **Runtime LLM prompt**: `resources/prompts/exercise-engine.md`, a byte-identical copy of `RUNTIME_SYSTEM_PROMPT.md`. Never rewrite it. Sibling feature prompts in the same folder: `tutor-chat.md` (chat), `mega-project.md` (Phases), `exam-prep.md`, `side-quest-engine.md`.
- **LLM provider**: `App\Services\LlmService` picks drivers (`app/Services/Llm/`) from `.env` — config in `config/ai.php`. **Chat and embeddings route separately**: `AI_PROVIDER` picks the chat driver (`freellmapi` | `gemini` | `openrouter` | `ollama` | `anthropic`); `AI_EMBED_PROVIDER` picks embeddings. If unset, `LlmService` defaults embeddings to the chat provider except `gemini`/`anthropic`, which fall back to `openrouter` (`app/Services/LlmService.php:28-31`) — **`freellmapi` has no automatic fallback**, it would try to embed via FreeLLMAPI itself unless `AI_EMBED_PROVIDER` is set explicitly (the shipped `.env` does set it). Embeddings must NEVER change model mid-corpus — stored 1536-dim `text-embedding-3-small` vectors are only comparable to query vectors from that same model. Current setup: `AI_PROVIDER=freellmapi` (FreeLLMAPI proxy on port 3001), embeddings = openrouter `openai/text-embedding-3-small`. Keys only in `.env`, never in code. Smoke test: `php artisan llm:test`. **Chat-only cross-provider fallback**: on top of each driver's own internal retries, `LlmService::chat()` catches any throw from the primary chat driver and retries once against `AI_FALLBACK_PROVIDER` (`config('ai.fallback')`, default `openrouter`) if one is configured, isn't the same as the primary, and has a usable key — logged as a `Log::warning`. Embeddings never use this fallback (same never-change-model-mid-corpus reasoning).
- **FreeLLMAPI integration**: `App\Services\Llm\FreeLlmApiDriver` connects to `FREELLMAPI_BASE_URL` (`http://127.0.0.1:3001/v1`) using bearer authentication via `FREELLMAPI_API_KEY`. Automatically load-balances across Gemini, Groq, GitHub Models, and OpenRouter free tiers.
- **Obsidian Vault Export**: `App\Services\ObsidianExportService` writes Markdown copies of generated and evaluated missions into an Obsidian Vault folder specified by `OBSIDIAN_VAULT_PATH` when `OBSIDIAN_EXPORT_ENABLED=true`. `php artisan study:export-obsidian {--id=*}` (`app/Console/Commands/ExportMissionsToObsidian.php`) re-exports on demand (all missions, or specific ids via repeated `--id=`).
- **Mission shape**: exactly FOUR drills (Setup/Task/Output/Concepts, concrete values) + exactly one closing **Boss Fight** that integrates every concept of the mission into a single realistic build — defined in `RUNTIME_SYSTEM_PROMPT.md` MODE 1. Extra concepts get combined inside drills, never dropped. Generation takes a learner-picked difficulty (Easy/Medium/Hard selects on dashboard + ingest confirm → `Requested difficulty:` line in the MODE 1 request) and a learner-picked drill count (number input, min 0 max 20, default 5 → `Requested drills:` line) plus a learner-picked Boss Fight count (min 0 max 10, default 1 → `Requested Boss Fights:` line; several Boss Fights split the concepts between them, every concept in at least one). Dashboard, Ingest, and Side Quest forms all share the same 0–20 drills / 0–10 bosses validation — `ExerciseService::generate()`/`generateFromConcepts()` reject drills=0 AND bosses=0 together (must pick at least one of either). The old Side Quest bool `$bossFight` checkbox was replaced by the same numeric `$bosses` param. Prompt revisits concepts from new angles when concepts < drills. Every mission ends with a `## Solutions` section (simple-first worked solution + `Concepts used:` per drill and Boss Fight, per user request — solutions ship WITH the mission, not after evaluation); MODE 2 compares the learner's work against those published solutions instead of restating them. phpunit.xml pins AI_PROVIDER/AI_EMBED_PROVIDER=openrouter so tests never follow a .env provider flip onto a real API.
- **Dashboard hero + roadmap progress**: dark `.hero` panel (the app's one loud surface; tokens/components in `resources/css/app.css`) greets `App\Support\LearnerName` (flat file `learner-name.txt`, saved via `POST /settings/profile`) and renders a `.progress-track` — one segment per roadmap phase, width ∝ week span, states done/current/upcoming from `RoadmapService::currentWeek()` vs topic week ranges; % covered = completed weeks / max(week_end).
- **Reset progress (scoped to the active track)**: `POST /settings/reset` (Settings → Danger zone) requires literal `RESET`; wipes only the **active track's** attempts, exercise_concept, exercises, struggle_notes, chunks, concepts, transcripts and chat session, and sets that track's roadmap `start_date` to today. The other track, this track's topics, personal instructions, and the learner name all survive untouched — instructions and the name are deliberately never cleared here since they're shared across tracks, not track data. Tests mock `File::put` (partialMock) so the real roadmap JSON is never rewritten by the suite.
- **Copies**: sister's install at `E:\Dev Projects\Study engine Memona`; shareable template at `E:\Dev Projects\study-engine-template` (blank API keys, `AI_PROVIDER=openrouter`, fresh `APP_KEY`, fresh DB + start_date, README quick-start). GOTCHA: `robocopy /XD` does NOT match multi-segment relative paths (e.g. `storage\app\private`) — leaked `learner-name.txt`/`laravel.log` had to be cleaned by hand; use absolute paths or post-copy cleanup.
- **Personal instructions (learner memory)**: free text saved from `/settings` (`POST /settings/instructions`, max 4000 chars) via `App\Support\LearnerInstructions` (flat file `learner-instructions.md` on the local Storage disk — no DB table). Injected into every MODE 1 request (`Learner's personal instructions:` section, honored per a MODE 1 rule that never overrides only-provided-concepts) and into the tutor system prompt via `ChatController::learnerState()`. **Feedback also drives selection**: `ExerciseService::reviewSelection()` flags reviewed concepts whose names contain any significant word (≥4 chars, filler filtered) of the instructions and puts them at the front of the review picks, due or not — so "dict methods are slipping" actually pulls those concepts into upcoming missions. Base `tests/TestCase` fakes the local Storage disk so tests never read the real learner files.
- **Boss Fight skeleton protocol (Boss Fights ONLY)**: every Boss Fight ends with a `**Protocol:**` block — first attempt must be a plain-English pseudocode skeleton (no Python), premature code gets rejected with one kind teasing line (boss-only concepts left unscored, drills scored normally), a sound skeleton earns the literal marker `Skeleton approved` in feedback plus the first architectural layer, then one layer per attempt. The evaluator is stateless, so `buildEvalRequest` now ships the last 5 attempts' `evaluation_md` (`Previous evaluations` section) — that marker IS the phase state. Tutor coaches the same way (`tutor-chat.md` Boss Fight coaching section).
- **Mission referencing**: every mission's number is its reference (`M{exercise_id}`, shown on exercise page/dashboard/history/chat empty-state). `App\Services\MissionReference::resolve()` parses chat messages for `M3`, `M3 D2`/`M3-D2`, `M3 B1`, or bare `D2`/`B1` (= newest mission), extracts the `## ` section from `mission_md` (drill by number, boss by ordinal) plus its `### Solution — {name}` block (matched by evocative name), and `ChatController` appends it to the LLM request as a `REFERENCED MATERIAL` block — the learner never pastes mission text.
- **Project audit (Phases → Submit)**: the app's free LLMs can't read a whole repository, so a finished Mega Project is audited by Claude Code. `GET /phases/{n}/audit-prompt` → `PhaseService::generateAuditPrompt()` fills `resources/prompts/project-audit.md` with the brief verbatim plus the milestone gates (`PhaseService::gatesFromPlan()` lifts only `✅ Checks` / `FINAL ACCEPTANCE CRITERIA` / `COMPLETE ONLY WHEN` out of the plan — never steps, whys or reference solutions) and a fixed 10-section report format. The learner pastes the prompt into Claude Code (read-only audit), then pastes the whole report into the Submit box; `evaluateMegaProject()` detects `# PROJECT AUDIT REPORT`. Enforced in code, not in prose: the `Audit ID:` line (md5 of brief + gates) must match the current standards, the report must contain sections 3, 5, 10 and end with `END OF REPORT` — otherwise `AuditReportRejected` (nothing sent to the model, input kept) — and any FAIL/NOT RUN verdict in the report's gate/constraint tables caps the score at 69. In audit mode the model gets brief + gates + report only (not the full plan/skeleton). Plain code submissions behave as before. **Alignment rule (user requirement)**: the brief is the contract — it must write down everything graded (MODE 1), the plan must cover every brief item (MODE 3 "Brief coverage" + a `## Brief Coverage` table, which `gatesFromPlan()` also passes to the audit), and the audit/grader grade ONLY the brief + gates, read literally; anything else is "Beyond the plan" / "Optional improvements", never scored. **Attempts & fix plans**: every graded submission is appended to `phase_progress.project_attempts` (JSON, last 10; a project graded before that column existed is rebuilt as attempt 1 by `attemptHistory()`); a resubmission sends the earlier attempts to the grader (`RESUBMISSIONS` rules in `mega-project.md`: FIXED / STILL OPEN / REGRESSED / OUT OF SCOPE) and the audit prompt gets a `RESUBMISSION CHECK` section. `GET /phases/{n}/fix-plan-prompt` → `generateFixPlanPrompt()` (`resources/prompts/project-fix-plan.md`) builds a prompt for Claude that writes a Fix Plan in the learner's usual plan format (the format rules are lifted live out of `mega-project.md`'s MODE 3 block, never copied) from the grader feedback + audit sections 3–6, 9, 10. GOTCHA: never split plan text with `preg_split('/\R/')` — without `/u`, `\R` matches byte `0x85`, which ends `✅` and cuts it in half.
- **Tutor chat**: `/chat` (`ChatController`) — session-held history (capped at 30 entries, `POST /chat/clear` resets), folded into one user string per request because drivers take a single user message; message max 20000 chars (learners paste code). Tutor replies containing drills (`**Task` marker) get a "Save as mission" button → `POST /chat/mission` (message index) → `ExerciseService::fromChat()` stores the reply as a pending mission with every existing concept named in the text attached as `review`, so chat practice runs the normal submit/evaluate/ladder loop; system prompt at `resources/prompts/tutor-chat.md` (beginner-focused, simple solutions first; knows the app's purpose/flow, can generate ad-hoc drills in chat with solutions last, teaches the write-first/AI-reviews-after workflow) + live learner state appended per request (`ChatController::learnerState()`: phase, ≤10 due concepts, ≤10 unresolved struggle notes).

## Data model

Eight tables in the original migration (`2026_07_09_000001_create_study_engine_tables.php`): `topics`, `transcripts`, `concepts`, `chunks`, `exercises`, `exercise_concept` (pivot), `attempts`, `struggle_notes`. Columns follow PROJECT_SPEC.md §4 exactly. `topics` has no timestamps (`Topic::$timestamps = false`). Later migrations added: `2026_07_23_000001_create_phase_and_exam_tables.php` (`phase_progress` — backs `PhaseProgress` model / `PhaseService::markPhaseCompleted`; `notifications`; `exam_prep_sessions` — backs `ExamPrepSession` model), `2026_07_23_100000_add_type_to_exercises.php` (`exercises.type`, default `'mission'`, distinguishes Side Quest missions from regular ones), and `2026_08_11_000001_add_mode_to_study_engine_tables.php` (adds `mode` string, default `'ai_security'`, to `topics`/`transcripts`/`concepts`/`chunks`/`exercises`/`phase_progress`/`notifications`/`exam_prep_sessions` for the dual-track system — see "Dual study tracks" above — and swaps `topics.phase_number`/`phase_progress.phase_number` from a single-column unique to a composite `(phase_number, mode)` unique; `attempts`/`struggle_notes`/`exercise_concept` deliberately got no `mode` column, they scope transitively through their parent).

Spacing algorithm (spec §5): ladder 1/3/7/14/30 days; score ≥ 70 promotes, < 70 is a lapse (halve interval, min 1 day, boost struggle note).

## Ingestion (Milestone 3)

`App\Services\IngestService`: `chunk()` splits ~2000 chars (~500 tokens) with 200-char overlap; `extractConcepts()` asks the chat model for strict JSON (`{topic_phase_number, concepts:[{name, summary}]}`, fences/prose stripped tolerantly); `store()` writes transcript + embedded chunks (one `embedMany` batch call) + concepts inside a transaction. New concepts get `next_review_at = tomorrow`; existing names (case-insensitive, global) are linked, never duplicated. `chunks.concept_id` stays null — retrieval (Milestone 4) will match concepts to chunks by cosine similarity, not stored links. Flow: `GET /ingest` → `POST /ingest/preview` (LLM, shows editable checklist) → `POST /ingest/confirm` (saves only checked concepts).

## Exercise engine (Milestone 4)

`App\Services\ExerciseService`: `selectConcepts()` returns `[new, review]` — new = non-retired with `interval_days = 0` (all of them; missions scale up); review slots (count ≈ ⅔ of new, floor 2 → ~60/40) fill with overdue concepts first (lapses desc, then most overdue) and then **backfill with not-yet-due reviewed concepts** (soonest `next_review_at` first) so past topics repeat in every mission (true interleaving — user requirement). Nothing new → up to 8 strictly-due only. Shared `reviewSelection()` also drives `generateFromConcepts()` (excludes the just-ingested ids). `latestPending()` = newest `status=pending` mission; the dashboard falls back to it when today has no mission ("Unfinished mission" banner) so work survives restarts/day changes. `retrieveChunks()` embeds each concept's name+summary and takes top-2 chunks by cosine in PHP. `generate()` is one-per-day (returns existing), sends the MODE 1 request (concepts with ids/roles/lapses, unresolved struggle notes, current phase+week, chunks) with the runtime prompt as system, stores the exercise + `exercise_concept` pivots (NOTE: pivot table name is non-alphabetical, must be explicit in `belongsToMany`). `RoadmapService::currentWeek()/currentPhaseTopic()` derive phase from `meta.start_date`. Dashboard `/` shows stats (due count, phase/week, streak = consecutive days with ANY app activity — `App\Support\ActivityLog` flat file `activity-days-{mode}.txt` (one per track), touched by the `RecordActivity` web middleware on every request, first touch backfills from exercise dates + attempt/transcript created_at, cleared by that track's reset) and renders `mission_md` via `Str::markdown` (html stripped) styled by the `.mission` CSS block in `resources/css/app.css` (no typography plugin).

## Transcript-driven drills (primary workflow) + UI

Ingest confirm has two buttons: "Save only" and "Save & generate drills" (`action=save_generate`). The latter calls `ExerciseService::generateFromConcepts(ids)` — the just-saved concepts (ids returned by `IngestService::store`) become [NEW], due reviews *excluding* those ids become [REVIEW] (cap ⅔·new). This path allows multiple missions per day; the dashboard button keeps one-per-day via `generate()`. Both share private `storeMission()`. `todays()` = latest of today; the dashboard itself shows only the current/pending mission (no mission-browser dropdown on `/` — `/history` is the actual page for browsing every past mission, paginated 20/page); `Exercise::title()` parses the first mission_md line. UI: design tokens + component classes (`btn`, `btn-accent`, `btn-outline`, `input`, `card`, `eyebrow`, `badge-*`, `stat-num`, `label`) live in `resources/css/app.css` (`@theme` + `@layer components`) — use them, don't hand-roll padding; `form[data-llm]` gets an automatic disabled/working state from layout JS. **The dev database holds real user study data — never `migrate:fresh` without explicit user consent.**

## Evaluation loop (Milestone 5)

`ExerciseService::evaluate()` sends MODE 2 (mission + pasted result + concept list with ids/roles) via `LlmService::chatJson()` (the shared tolerant JSON parser lives on LlmService) — the system prompt is picked by `$exercise->type` exactly like generation does (`side-quest-engine.md` for `side_quest`, `exercise-engine.md` for everything else), so Side Quest submissions grade against Side Quest's own multi-attempt Boss Fight protocol instead of the regular mission's single-submission one. Stores an `Attempt` (score = rounded avg of per-concept scores), then `applyLadder()` per concept: ≥70 promotes to the next rung of `[1,3,7,14,30]` (capped at 30), <70 increments lapses, halves interval (min 1) and creates/boosts an unresolved struggle note — skipped when the evaluation already suggested a note for that concept. Hallucinated concept_ids are ignored; unscored concepts are skipped, not punished. `addOwnNote()` = learner's free-text note, weight 2, all exercise concepts. OpenRouterDriver retries once on empty completions / 200-with-error bodies (free-tier flakiness — real, observed). Resubmission is allowed and re-runs the ladder.

**Inline drills (exercise page)**: `ExerciseController::show()` renders `mission_md` per `## ` section (`MissionReference::sections()`, fence-aware, tags `D{n}`/`B{k}`) so every drill gets a Copy button (raw section markdown) + an inline answer box, and every Boss Fight gets Copy only (those are done in VS Code). `POST /exercise/{id}/drill/{Dn}` → `ExerciseService::checkDrill()` scores that one drill against its published solution with `resources/prompts/drill-check.md` (JSON `{score, feedback_md}`), upserts `drill_attempts` (one row per `(exercise_id, drill_key)`, no `mode` column — scopes through exercise). Quick checks never touch the ladder; `buildEvalRequest` ships them to MODE 2 as part of the submission, so "Your result" may be left empty when drills were checked inline. Page JS (bottom of `exercise/show.blade.php`) submits via fetch and live-updates the per-drill badges + the total bar under the mission.

## Updates for distributed copies (STANDING RULE — do this without being asked)

Other people run offline copies of this app (sister's install at `E:\Dev Projects\Study engine Memona`, template users). **At the end of EVERY session that changed app files, run `php artisan update:package "<one-line summary of the changes>"`** — it diffs the tree against `updates/manifest.json` (md5 per shippable file) and cuts `updates/update-NNN-<date>/` containing the changed files, an auto-generated README, `apply-update.ps1` (data-safe installer: version gate, backup, robocopy, deletions, .env key append, migrate, cache clear), and bumps `version.txt` + the manifest. Never shipped: `.env`, sqlite files, `storage/**`, root roadmap JSON, logs. `--dry` previews; `--baseline=<dir>` rebuilds the manifest from a distributed copy. Recipients apply packages **in order** (the applier enforces it). If a session changes the roadmap JSON structure or anything under `storage/`, say so in the package notes — those paths are deliberately not distributed. This includes `storage/app/roadmap/Laravelstudy.json`: it's excluded by the same `storage/` rule as the AI roadmap file, so recipients need it called out explicitly (or copied by hand) to use the Laravel Web track at all.

## Conventions

- Blade + Tailwind via Vite; no SPA framework. Keep dependencies minimal, first-party Laravel features preferred.
- Seeding = `php artisan db:seed` (DatabaseSeeder delegates to RoadmapService::syncTopics).
- Debug/verification route: `GET /debug/topics`.
- Build milestone-by-milestone per spec §7; stop after each for user confirmation.
